# Выделение периода оказания услуги в строках табличных частей: сравнение моделей

Задача: по тексту наименования строки (`НаимТов` СЧФ и УПД) получить период (начало и конец, ГГГГ-ММ-ДД) либо «нет периода».
Совпадение считается по точному равенству обеих дат. Файлы: `eval.json` (эталон), `xml_lines2.txt`, `pred_*.json`, `errors_*.json`, `report_metrics.md`.

## Данные (658 строк)
- 398 «обычных» строк из PDF-счетов (`experiment_invoice_lines/work/tab_0.pkl`);
- 150 «сложных» из тех же PDF (диапазоны, одиночные даты, несколько дат в строке);
- **110 строк `НаимТов` из `events_26_in.xml`, только типы `Invoice` (СЧФ) и `UniversalTransferDocument` (УПД)**: 94 с периодом, 16 без него (в основном «Строительство/Модернизация … согласно ДС от …», где даты — реквизиты договора, а не период).
  Первая версия XML-выборки брала ещё акты (`PerformedWorkAcceptanceCertificate`, `XmlAcceptanceCertificate`, `ServiceDetails`) — это был неправильный источник, выборка заменена, все модели пересчитаны.
- Итого 87 строк без периода.

## Что делает каждый вариант
- **Giga-480M — энкодер, генерировать не умеет.** Проверены (а) ранжирование кандидатов-фрагментов по сходству контекста с запросом, (б) токенный тегер «входит в период» поверх замороженных состояний (обучен на 3500 PDF-строках; диапазонов в обучении почти нет — отсюда 30% на диапазонах).
- **rubert-base-pii-ner**: класса даты у модели нет (README исключает `DATE_TIME`), «как есть» дат не находит. Энкодер дообучен с головой O/B-DATE/I-DATE (3 эпохи, ~1 мин, 4900 текстов: 3500 PDF-строк с разметкой по правилам + 1400 синтетических с диапазонами и датами договоров), затем связывание (`link.py`): две соседние даты между «по/до/–» (в т.ч. «Дата начала … Дата окончания», время между ними) → диапазон; недостающие месяц/год у начала берутся у конца; «январь – март 2026» → диапазон месяцев; одиночная сущность → месяц/квартал целиком или день; сущности без даты («09:42») отбрасываются.
- **DeepPavlov `ner_ontonotes_bert_mult`** (метка `DATE` есть в схеме OntoNotes; русские лучше не обучены, мультиязычный BERT): без дообучения. Модель находит области-даты (часто «период с 01.04.2026 по 30.04.2026» одной сущностью, и даты договоров тоже). Код: внутри области выделяются атомарные даты, даты после «от/№/ДС/акт» отбрасываются, при нескольких датах приоритет у стоящей после «за/период/в/на» (до этого правила результат был 86.8%), затем то же связывание. Запуск — в отдельном окружении Python 3.10 (`.venv_dp`), в pip-пакете DeepPavlov пришлось поправить загрузку весов (`strict=False`: лишний ключ `position_ids`).
- **Qwen**: один промпт на 7 примеров, greedy. Qwen 3.5-9B и 4B на v1 часто отвечали «нет» на явные «за январь 2026 г.», особенно рядом с «УПД №…»/«№ … от …»; v2 убирает из правил слова про УПД/акты/заявки. 27B: рассуждение не отключается через API, на 16 строках (в основном «Физическая охрана … за Март 2026») не хватило 1500 токенов — пустой ответ, засчитан как ошибка.

## Сравнение с регулярными выражениями
Эталон сам построен регулярками (`gold.py`), поэтому «полный» набор дал бы на нём 100% по построению — это не результат. В таблице два независимо написанных набора (`run_regex.py`, другая структура кода): базовый (диапазон дат, «месяц год», одиночная дата вне «от/№») и расширенный (+ кварталы, «25 по 31 мая», «январь – март», «Дата начала/окончания», двузначный год, «23 апреля 2026»).
- Базовый набор: 89.1%; на диапазонах 48.8%, на сложных PDF 62.7%, ложных срабатываний 0.
- Расширенный: 97.4%, ложных срабатываний 0, 17 ошибок: диапазон «с «21» марта 2026 года по «07» июня 2026 года», одиночные даты в строках с несколькими, «показания счетчика на 01.06.25г.», опечатка «Дата начла».
- **Это сравнение завышает регулярки**: писал оба набора один человек, расширенный я составлял, зная формы из выборки, а эталон — те же правила. Результат показывает «насколько согласны два набора правил», а не точность на новых данных. Один баг в наборе (дата без границы слева) был исправлен после первого прогона.
- Практический вывод: на строках из этих счетов регулярки конкурентны с любой моделью и в сотни раз быстрее; модели оправданы там, где формулировки заранее неизвестны (проверить это можно только на эталоне, размеченном вручную независимо от правил).

## Выводы
1. **Лучший по точности — rubert-base-pii-ner с дообучением и связыванием (98.8%)** и при этом в ~1000 раз быстрее Qwen 27B. Но он требует обучающих данных: метки получены тем же правилами, что и эталон, поэтому честнее всего смотреть на XML-страту (формулировок из неё в обучении не было): 97.3%.
2. **DeepPavlov без дообучения даёт 92.7%** — близко к Qwen 3.5-4B (93.8%), быстрее в ~30 раз. Слабые места: диапазоны (72%) и одиночные даты (61%) — модель часто режет «с 01.04.–30.04.2026», пропускает «Март 2026» после точки, не видит дату без слова «за».
3. **Qwen 3.8-27B (96.4%)** точнее мелких Qwen, но на ~7–8 с на строку; потери — пустые ответы при исчерпании токенов.
4. **Giga-480M как самостоятельный извлекатель не подходит** (тегер 86.3%, диапазоны 30%); режим «кандидаты» (95.1%) — не извлечение, а выбор из готовых кандидатов.
5. Размер Qwen сам по себе результат не определяет: 9B хуже 4B из-за чувствительности к формулировке промпта.
6. Оставшиеся ошибки у всех: «февраль 26г» (двузначный год), строки с несколькими датами («охрана 14.12.2025 … за Декабрь 2025» — эталон берёт месяц), «12/2025».

## Ограничения
- **Эталон построен правилами** (`gold.py`), вручную проверен лишь на нескольких десятках строк; на 6 строках поправлен руками. Giga в режиме кандидатов использует тот же детектор кандидатов; rubert и DeepPavlov используют атомы-регулярки при нормализации. Правило «месяц важнее одиночной даты» — решение автора эксперимента, а не данные.
- Связывание для rubert-pii правилось по ошибкам на этой же выборке (время между датами, «Дата начала/окончания», «январь – март»), для DeepPavlov — правило приоритета «за/период»; оценка оптимистична.
- Строки «месяц без года» исключены (нет однозначной даты). Один прогон каждой модели, без повторов.
- PDF-выборка — один корпус счетов; XML — 110 формулировок из `events_26_in.xml` (одна выгрузка).
- Период в заголовках XML (`ПериодС/ПериодПо` в `ИнфПолФХЖ1`) в смотренных мной актах подряда — сроки проекта/ДС, не период строки. Для СЧФ/УПД я это не проверял и в эксперименте не использовал.
